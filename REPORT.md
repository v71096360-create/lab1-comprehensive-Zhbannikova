## 2. Сравнительный анализ технологий

### 2.1. Матрица принятия решений

| Критерий                           | Вес | PostgreSQL (1-5) | MongoDB (1-5) |
|                                    |      |                 |               |
| Поддержка ACID-транзакций          | 0.40 | 5               | 3             |
| Целостность данных и строгая схема | 0.30 | 5               | 3             |
| Производительность чтения          | 0.15 | 4               | 5             |
| Гибкость схемы                     | 0.10 | 3               | 5             |
| Экосистема и простота поддержки    | 0.05 | 5               | 4             |
| **ИТОГО (Сумма весов)**            | **1.00** |      |                 |

### 2.2. Расчет и обоснование выбора

**Формула:** Оценка = Σ(Вес_критерия × Балл_кандидата)

**PostgreSQL:**
- (0.40 × 5) + (0.30 × 5) + (0.15 × 4) + (0.10 × 3) + (0.05 × 5)
- = 2.0 + 1.5 + 0.6 + 0.3 + 0.25
- = **4.65**

**MongoDB:**
- (0.40 × 3) + (0.30 × 3) + (0.15 × 5) + (0.10 × 5) + (0.05 × 4)
- = 1.2 + 0.9 + 0.75 + 0.5 + 0.2
- = **3.55**

**Вывод:** Победитель — **PostgreSQL** (4.65 > 3.55). Для финансовых транзакций критически важна надежность (ACID) и целостность данных, где PostgreSQL набирает максимальные баллы.

## 5. Обратное проектирование и планирование ревью

### 5.1. Анализ алгоритма

**UML-диаграмма деятельности** для алгоритма `calculate_cart_total`:

![UML Diagram](docs/uml_diagram.png)

**Описание алгоритма:**
1. Начальная цена равна сумме корзины (`price = cart_sum`)
2. Если сумма > 15000, применяется базовая скидка 15% (`price = cart_sum * 0.85`)
3. Цикл перебора промокодов:
   - Если промокод "SUMMER" — скидка 500 рублей
   - Если промокод "VIP" — скидка 10%
4. Применение скидки по уровню лояльности:
   - tier 1 — скидка 3%
   - tier 2 — скидка 7%
5. Финальное ограничение: цена не может быть меньше 70% от исходной суммы

**Выявленные "запахи кода" (Code Smells) в legacy-фрагменте:**

1. **Магические числа:** Коэффициенты `0.85`, `500`, `0.90`, `0.97`, `0.93`, `0.70` жестко зашиты в код. Необходимо вынести их в константы с понятными именами (например, `BASE_DISCOUNT_RATE = 0.85`).

2. **Отсутствие валидации входных данных:** Нет проверки, что:
   - `cart_sum` — положительное число
   - `tier` — допустимое значение (1, 2 или другое)
   - `promos` — список строк

3. **Нарушение принципа единой ответственности (SRP):** Функция одновременно:
   - Считает базовую скидку
   - Применяет промокоды
   - Применяет скидку по уровню лояльности
   - Проверяет минимальную цену
   
   Необходимо разбить на несколько функций.

4. **Отсутствие обработки edge cases:** Что если `promos` — пустой список? Что если `cart_sum = 0`?

## 6. Заключение

Настроенные процессы создают "защитный периметр" вокруг кода микросервиса «Расчет корзины и скидок»:

1. **Выбор PostgreSQL** обеспечивает надежность финансовых транзакций благодаря поддержке ACID и строгой целостности данных.

2. **Защита ветки `develop`** (требование PR) предотвращает прямые пуши в основную ветку разработки, форсируя код-ревью перед слиянием.

3. **Автоматический линтинг** через GitHub Actions ловит ошибки кодстайла на этапе PR, не позволяя им попасть в основную ветку. Метод "Сломать и починить" подтвердил работоспособность Quality Gate.

4. **UML-диаграмма** документирует алгоритм расчета скидок, делая его понятным для новых разработчиков.

5. **План код-ревью** с измеримыми критериями и механизмом эскалации обеспечивает единообразный подход к проверке кода.

**Итог:** Все эти процессы значительно снижают риск внесения дефектов в расчеты скидок, что критически важно для финансовой репутации стартапа системы лояльности. Ошибки в расчете баллов или промокодов могут привести к прямым финансовым потерям и недоверию клиентов.
